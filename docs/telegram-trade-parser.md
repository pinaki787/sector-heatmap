# Telegram Trade Parser

The existing FYERS Trade Parser and its WhatsApp queue retain their route. The separate Telegram Trade Parser accepts pasted text or new channel posts and routes each ticket to explicitly selected FYERS or Delta Exchange India.

## Connect

Use a dedicated Telegram bot with membership/access to the chosen channel. Enter its token only in the local masked Bot token field and the channel's @username or numeric -100 ID. Save configuration, then Verify channel access. This performs getMe, getChat, getChatMember and getWebhookInfo; it does not send messages or change an existing webhook. Tokens are stored only in `.private/telegram-review.json` with owner-only permissions and never returned by status. A subscribed Telegram user account alone does not give a bot channel access. Bot API updates cover new posts/edits, not arbitrary past channel history.

## Submission

Default confirmation mode queues messages for Load recommendation → Parse recommendation → Submit order. This one deliberate Submit is the confirmation; there is no preparation step, typed phrase or modal. Broker changes or text edits invalidate the parsed ticket. Tickets expire after 120 seconds; channel recommendations expire after five minutes.

Select broker and positive whole quantity: FYERS lots or Delta contracts. Delta matches exact listed symbols without automatic ATM mapping. Limit and stop-limit entries use native broker terms. Delta stop-limit triggers use last-traded price, a tick-aligned trigger beyond the current executable quote, and a limit one tick beyond the trigger in Auto. Broker authentication, fresh executable quotes, contract metadata, wallet/funds gates, pending-order/position guards and native validations run before submission. A held/running Delta strategy blocks Telegram entries and is never adopted or changed. Recommendation stop/targets are displayed as a plan; protective exits are not automatically created by this parser.

Auto submission is default off. Checking it and deliberately starting configured polling authorizes new actionable channel recommendations to submit to the selected broker and quantity without per-order confirmation. Startup drains the pending update backlog as review records before arming Auto. Explicit BUY/SELL/SHORT, complete parsing, exact contract and fresh original message timestamp are required. Duplicate channel/message IDs and edits do not automatically resubmit. Ambiguous, expired or invalid messages remain blocked with diagnostics. Broker acceptance is not a fill. Queue responses include broker order/filled quantity where available; Refresh broker order status reconciles attributed Delta request IDs or exact FYERS order IDs and trade snapshots. Unknown outcomes are never blindly retried.

Polling and Auto never resume on application restart. Stop polling disables future discovery/submission; it does not cancel already accepted broker orders. Existing held positions are unaffected.

## Subscriber account · receive only

Use this route when you subscribe to the advisory channel but cannot add a bot. It uses the official Telegram user-client API through pinned Telethon 1.45.0. Install the optional dependencies in the same Python runtime as the dashboard: `python3 -m pip install -r requirements-telegram.txt`. A missing or mismatched version is reported by the local setup form and connection is blocked.

Choose **Subscriber account · receive only**. The prepared advisory ID is `-1003660684605`; verify the returned channel title before starting. Obtain your own API ID and hash from https://my.telegram.org under API Development Tools. Enter them in the local masked fields and Save configuration. Enter your account phone with country code, request the login code, enter the received code locally, and enter your existing two-step verification password only if requested. Do not put these values in chat. Telegram Web login remains independent; browser sessions are never extracted.

Credentials are owner-only in `.private/telegram-subscriber.json`; the separate session and SQLite sidecars reside in owner-only `.private/telegram-session/`. The session provides account-level authorization: the receive-only restriction is enforced by this application, not a Telegram scoped token. Keep this directory out of Git, exports and routine backups; revoke this client in Telegram Settings → Devices if needed. Login code, phone and 2FA password are not persisted. Telethon entity persistence is disabled, avoiding a stored account-wide dialog cache; only selected-channel text/captions and review metadata are retained (maximum 500 queue records). Dialog metadata is inspected in memory to resolve legitimate selected-channel access. No message-send, join, read-receipt or contact-change calls are made. Disconnect closes the client but retains its local session for explicit reuse.

**Verify channel access** authenticates and resolves the selected joined broadcast channel or supergroup but does not start reception. **Start receiving · review only** records the latest message ID as its baseline and accepts newer posts. It does not import earlier history. Incoming posts and edits are deduplicated by channel/message ID and content revision. Edits invalidate older parsed tickets; previously submitted messages remain unavailable for resubmission. A bounded 30-second reconciliation recovers missed newer posts into manual review only. More than 200 missed posts stops reception and reports a gap instead of silently claiming completeness. A new explicit Start establishes a new baseline and skips stopped-period backlog. Restart leaves reception stopped even when a saved session exists. Auto submission is unavailable on this route; Load → Parse → manual Submit remains the existing separate LIVE-order path. Recommendation receipt itself does not trade or create protective exits. Manual pasted recommendations remain available without any Telegram connection.

References: https://core.telegram.org/api, https://core.telegram.org/api/auth, https://docs.telethon.dev/en/stable/concepts/sessions.html.

The advisory peer `-1003660684605` is a Telegram supergroup (`megagroup`), despite its advisory/channel presentation. Subscriber verification accepts joined supergroups and broadcast channels, always matching the exact marked peer ID; it does not change membership.

## User-click ATM option tickets · Paper and Live

The **Bought ATM Call / Put · Renko owner** ticket product is separate from the retained legacy exact-native-contract path. Paste a recommendation or Load a received item, then Parse. BTCUSD/ETHUSD/XAUTUSD directional recommendations map to BUY calls when bullish and BUY puts when bearish. XAUUSD requires the visible **XAUUSD → XAUT bought options** proxy selection. This is gold-token derivative execution, never spot buying; it is not a claim that the two prices are equivalent.

The preview resolves the actual nearest unexpired ATM option, showing exact symbol, strike, product settlement timestamp in IST, hours remaining, bid/ask, multiplier and underlying exposure per contract. Gold product settlement timestamps take precedence over generic BTC/ETH schedules. No weekly/monthly expiry is fabricated or silently selected. Whole contract quantity starts blank; indicative premium is contracts × contract multiplier × option ask, before fees. Review the explicit Paper/Live selector and Renko timeframe/EMA/Supertrend exits, then check the ticket review acknowledgement. Other saved Renko exit/risk settings remain in the preview profile; recommendation stop/targets do not become option-premium orders or overwrite Renko exits.

**Submit is immediate user-confirmed option entry**, priced by the fresh option ask through the existing marketable LIMIT IOC adapter. Recommendation underlying entry/stop/target levels remain references; Submit does not create an underlying-trigger watch or transfer XAUUSD levels to XAUT. Original gold source/basis remains a prerequisite for any future unattended conditional execution. A changed ATM symbol/expiry, stale quote, active instance, existing owned/pending orders, account or position conflicts, or failed broker validation blocks submission. Paper uses the existing simulated executable-quote lifecycle and never calls native broker order submission. Live acceptance/pending and confirmed fills are distinguished.

The per-underlying Renko instance owns the initial durable order intent and reconciliation, including terminal partial fills, instead of adopting a position after the fact. Its automatic strategy entry gate stays disabled; it manages only this entered position using the displayed exit profile. Once flat it stops, avoiding unrelated signal re-entry. Pending/rejected/unknown outcomes are never blindly resent. Restart retains ownership/journal and leaves monitoring stopped for explicit recovery. Telegram reception and order entry are separate. No unattended Auto option submission is enabled by this ticket feature.

## Unattended Paper options

Explicit **Start unattended Paper · 1000 contracts** authorizes only simulated bought ATM options for new subscriber posts. It starts verified subscriber reception if needed and establishes a fresh baseline. BTCUSD/ETHUSD BUY maps to that underlying’s call; SELL/SHORT maps to its put. XAUTUSD uses its own options. Contract units come from fresh product metadata. XAUUSD remains blocked in unattended mode because XAUT prices cannot verify an original forex trigger.

The watcher uses fresh matching Delta last-traded prices, waits for BUY ABOVE / SELL BELOW strictly, and rechecks the recommendation at final Paper-entry preflight. Recommendations expire after five minutes. Missed posts, edits, stopped-period history and identical text never replay. A durable claim precedes entry; uncertain outcomes require reconciliation and are not retried. Each per-underlying Renko instance must be flat/stopped, owns simulated fills and manages configured exits, then stops when flat. An occupied instance blocks competing recommendations.

Paper defaults to 1000 whole contracts; Live requires explicit selection and reviewed Submit. Parse itself previews. Stop unattended Paper prevents new entries while existing owned Renko exits continue. Restart leaves reader, watcher and management stopped for explicit recovery; historical watches are not resumed. No live broker orders are sent by the Paper pipeline. The earlier receive-only/manual-only descriptions apply to the transport/legacy workflow; this explicitly armed Paper watcher is a separate opt-in coordinator.

### Immediate Paper entry on receipt (current policy)

The owner's later instruction supersedes trigger-waiting for the unattended PAPER pipeline: a genuinely new, fresh recommendation is parsed and submitted immediately with 1000 whole bought ATM option contracts. Entry conditions, stop and targets remain references; no claim is made that an advisory trigger occurred. XAUUSD uses the previously disclosed XAUT proxy in Paper only. Greetings are IGNORED_CHATTER. The five-minute queue-freshness check remains a stale-receipt guard, not a wait-for-trigger period. Reconnect backlog, edited posts and duplicates remain excluded. Live execution still requires manual reviewed Submit. Existing expired records are not replayed.
